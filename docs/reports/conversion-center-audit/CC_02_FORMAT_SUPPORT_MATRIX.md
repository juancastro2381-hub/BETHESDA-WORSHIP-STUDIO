## 1. Scope & Definitions

This document defines the complete multi-format input/output support matrix for the planned **Bethesda Musical File Conversion Center**.

### 1.1. Source Input Categories (5 Domains)
1. **Category 1 — PDF Musical Documents:**
   - **Type 1A — Vector Sheet Music PDF:** Digital PDF generated by engraving software (Finale, Sibelius, MuseScore) with embedded vectors/fonts.
   - **Type 1B — Raster Scanned Sheet Music PDF:** Scanned physical sheet music pages with pentagrams, clefs, and notes.
   - **Type 1C — Chord-over-Text Cancionero PDF:** Lyric and chord songbooks (single or multi-column, e.g., *CMB AZUL*, *CMB MUSIC*).
2. **Category 2 — Raster Images:**
   - PNG, JPEG, TIFF, WEBP containing scanned or photographed scores or chord sheets.
3. **Category 3 — Audio Recordings:**
   - Monophonic & Polyphonic audio files (WAV, MP3, FLAC, M4A, OGG, AAC).
4. **Category 4 — Video Sources:**
   - Authorized streaming URLs (YouTube, Vimeo) and direct video containers (MP4, MKV, WebM).
5. **Category 5 — Structured Musical Formats:**
   - MusicXML (v3.0, v4.0, `.musicxml`, `.mxl`).
   - ChordPro (`.chordpro`, `.cho`, `.crd`).
   - Standard MIDI Files (Type 0, Type 1, `.mid`, `.midi`).
   - Bethesda Structured Written Notes (JSON).

### 1.2. Target Output Formats (8 Formats)
- **O1: Canonical Model (`CanonicalMusicPayload`):** Platform-native lossless musical representation in PostgreSQL.
- **O2: MusicXML 4.0 (`.musicxml` / `.mxl`):** Standard interchange format for notation software.
- **O3: ChordPro (`.chordpro`):** Industry standard for chord charts and digital lead sheets.
- **O4: Standard MIDI File (`.mid`):** Standard multi-track event sequence for DAWs and synthesizers.
- **O5: Engraved PDF Score:** High-resolution vector PDF rendered by an engraving engine.
- **O6: Rendered Audio (WAV / MP3):** Synthesized audio generated from notes and tempo maps.
- **O7: Lyrics Only (`.txt`):** Text extraction devoid of chords or musical symbols for projections.
- **O8: Guitar Tablature / Voicings (`.txt` / JSON):** ASCII tabs and chord fingering diagrams.

## 3. Deep Conversion Path Analysis

### 3.1. Structured Inputs (MusicXML, ChordPro, MIDI)

#### Path 5A -> All Targets (MusicXML Source)
- **To Canonical (O1):** Fully implemented in `MusicXmlImporter` with 480 TPQN normalization, unmetered measure support, multi-voice tracking, and zero pitch fabrication.
- **To MusicXML (O2):** Requires a dedicated `CanonicalToMusicXmlSerializer`. Feasibility is immediate (deterministic XML generation).
- **To ChordPro (O3):** Requires extracting harmony tags and lyrics syllables from `CanonicalMusicPayload`. Chords placed over corresponding lyric syllables. Feasibility: high.
- **To MIDI (O4):** Requires converting canonical ticks (480 TPQN) to MIDI delta-ticks, serializing NoteOn/NoteOff events per voice/track. Feasibility: immediate.
- **To Engraved PDF (O5):** Can be achieved server-side via headless Chromium rendering of OSMD or via Verovio CLI.
- **Information Loss:** MusicXML contains rich engraving layout metadata (stem directions, beam groupings, page breaks) that are simplified in the canonical model. Re-exporting will produce musically identical notation but may alter exact graphical line wraps unless layout hints are preserved.

#### Path 5B -> All Targets (ChordPro Source)
- **To Canonical (O1):** Fully functional. Creates measures with `chords` and `lyrics`, but **zero notes**.
- **To MusicXML (O2):** **STRICTLY BLOCKED**. ChordPro has no note pitches, staves, or durations. Generating a standard notation score from ChordPro requires inventing melody notes, which violates the core zero-fabrication contract.
  > [!IMPORTANT]
  > When a user requests ChordPro -> MusicXML, the Conversion Center must present a clear notice: *"ChordPro documents contain harmonic progressions and lyrics only. Traditional sheet music notation cannot be generated without inventing melody notes. You may export as a Chord Sheet PDF or Digital Music Stand view."*
- **To MIDI (O4):** **BLOCKED for Melody / OPTIONAL for Backing Track**. Generating a melodic MIDI track is blocked. However, a deterministic harmonic accompaniment (chords arpeggiated or played as sustained blocks) is feasible *only if* explicitly labeled as *"Generated Accompaniment"* rather than original music.
- **To Lyrics Only (O7):** Trivial regex strip of `\[.*?\]` chord brackets and metadata tags.

#### Path 5C -> All Targets (MIDI Source)
- **To Canonical (O1):** Backend adapter exists (`midi-adapter.ts`). Normalizes MIDI ticks to 480 TPQN, extracts pitch and duration.
- **To MusicXML (O2):** Feasible via quantization. MIDI contains raw performance timings; conversion requires metric quantization (e.g., snapping to 16th notes or triplets) to generate readable sheet music notation.
- **To ChordPro (O3):** Requires an automated harmonic analysis algorithm (e.g. Krumhansl-Schmuckler or template matching on pitch classes per bar) to infer chord symbols from polyphonic notes.
- **Fidelity & Limitations:** MIDI has no inherent concept of enharmonic spelling (C# vs Db), key signatures (unless encoded in meta events), or lyric text (unless encoded in track text events). Quantization heuristics may introduce slight rhythmic rounding.

### 3.2. Visual Documents (PDF Scores & Raster Images)

#### Path 1A / 1B / 2 -> MusicXML & Canonical (Optical Music Recognition)
- **Current State:** Stubbed / Mocked (`StandardOmrProvider` returns empty measures or test fixture).
- **Engine Required:** Headless OMR Engine (e.g., Audiveris CLI in worker container or modern Deep Learning OMR model like oemer/Calvo-Zaragoza).
- **Workflow:**
  1. Image preprocessing (deskewing, binarization, staff line removal/detection).
  2. Symbol detection (clefs, accidentals, noteheads, stems, beams, flags, rests, bar lines).
  3. Semantic assembly (pitch resolution relative to clef, duration calculation, measure grouping).
  4. Generation of preliminary draft proposal (`isAiDraft: true`).
  5. Mandatory human verification and correction interface.
- **Zero-Fabrication Guard:** Ambiguous or low-confidence symbols must be flagged with bounding boxes in `unrecognizedRegions`, never silently replaced with default notes.

#### Path 1C -> Formats (Cancionero / Chord-over-Text PDF)
- **Current State:** Functional via `pdf-chord-extractor.ts` and `chord-sheet-converter.ts`.
- **Outputs Available:** ChordPro (O3), Lyrics Only (O7), Guitar Voicings (O8).
- **Outputs Blocked:** Sheet Music (O2) and MIDI Melody (O4) are blocked due to zero melody notes in the source.

### 3.3. Audio Recordings (WAV, MP3, FLAC, M4A)

#### Path 3 -> Canonical & MusicXML (Audio to Score)
- **Current State:** Non-existent (`RECOGNITION_UNAVAILABLE`).
- **Engine Required:** Polyphonic Pitch Transcription Engine (e.g., Spotify's Basic Pitch or ByteDance's Piano Transcription).
- **Workflow:**
  1. Decoding & resampling to mono 22,050 Hz.
  2. Neural inference generating note activation matrices, onset probabilities, and pitch bend contours.
  3. Note thresholding & contour tracking.
  4. Quantization to metric grid (480 TPQN).
  5. Packaging into `CanonicalMusicPayload`.
- **Fidelity & Limitations:** Full polyphonic audio transcription of complex multi-instrument worship recordings is an imperfect MIR problem. Melody/vocal or solo piano transcription reaches 80-92% accuracy, while full band mixes suffer from note collisions, drum transients, and harmonic bleed.
- **Zero-Fabrication Contract:** Must always flag raw audio transcription as `isAiDraft: true` and require human review. Confidence thresholds must reject dubious phantom notes.

#### Path 3 -> ChordPro (Audio Chord Recognition)
- **Engine Required:** Chromagram extraction (e.g. NNLS Chroma, Essentia, or Madmom Chord Recognition).
- **Workflow:** Frame-by-frame chroma vector extraction -> Chord template correlation -> Viterbi decoding over chord state sequence.
- **Feasibility:** High. Chord recognition from audio is computationally lightweight and achieves 75-85% accuracy on common tonal progressions.

#### Path 3 -> Lyrics (Audio to Text)
- **Engine Required:** OpenAI Whisper / Whisper.cpp (self-hosted, CPU-quantized `base` or `small` model).
- **Workflow:** Audio transcription -> Timed word/syllable alignment.
- **Fidelity:** Very high (>95% on clean Spanish/English vocals).

### 3.4. Video Sources (YouTube, Vimeo, Video Uploads)

#### Path 4 -> All Targets
- **Current State:** Video URLs are validated against SSRF and stored as references. No audio is extracted.
- **Engine Required:** FFmpeg containerized worker + yt-dlp (for authorized video platforms where permitted) or direct browser audio capture.
- **Workflow:**
  1. Video audio stream extraction via FFmpeg: `ffmpeg -i input.mp4 -vn -acodec pcm_s16le -ar 44100 -ac 2 audio.wav`.
  2. Pipe extracted audio directly into the Audio Processing Pipeline (Path 3).
- **Legal & Technical Boundaries:** To respect YouTube and Vimeo terms of service, the preferred route is direct audio/video upload by the worship team. When URLs are supplied, the system must verify rights or restrict to authorized educational/church domains.

## 4. Information Loss & Degradation Risk Analysis

| Conversion Route | Primary Sources of Information Loss / Artifacts | Mitigation & Defensive Strategy |
| :--- | :--- | :--- |
| **MusicXML -> ChordPro** | Melody notes, rhythms, dynamics, articulations, and staves are completely discarded. | Explicit confirmation prompt: *"Converting MusicXML to ChordPro discards all musical notation and keeps only chords and lyrics."* |
| **MIDI -> MusicXML** | Missing enharmonic spellings (e.g. choosing between F# and Gb); tempo fluctuations create complex tuplets unless quantized. | Musical key context algorithm (Krumhansl-Schmuckler) selects proper spelling. Configurable quantization grid (quarter, 8th, 16th, triplet). |
| **Audio -> MIDI / Notes** | Phantom notes caused by percussive transients; dropped notes during quiet vocal tails; lost chord inversions. | High-pass/low-pass filtering; transient masking; adjustable note sensitivity slider in UI; mandatory review step. |
| **Scanned PDF -> MusicXML** | Optical noise, degraded ink, curvature in scanned pages lead to missing accidentals or misread flags. | Image binarization (Otsu thresholding); confidence scoring per measure; bounding-box audit overlay. |
| **Vector PDF -> ChordPro** | Multi-column songbooks can interleave lyrics if column detection fails. | Spatial X-coordinate clustering in `pdf-text-extractor.ts` separates columns before parsing. |

## 5. Architectural Guardrails for the Conversion Center

1. **The Hub-and-Spoke Invariant:**
   All multi-format conversions should pivot through `CanonicalMusicPayload` whenever musical notes or chords are involved. Direct Point-to-Point conversions (e.g. Audio -> FFmpeg -> Whisper -> Plain Text) are reserved for non-canonical extraction.
2. **Deterministic Precedence:**
   Deterministic converters (MusicXML, MIDI, ChordPro transpilers) run synchronously with zero latency. Probabilistic/ML engines (OMR, Audio transcription, Whisper) run asynchronously through background worker queues.
3. **Transparent Capability Badges:**
   In the user interface, every target format must display an unambiguous badge:
   - **Verificado / Nativo:** 100% deterministic conversion without loss.
   - **Aproximado / IA:** Probabilistic conversion requiring human review.
   - **No Disponible:** Blocked by zero-fabrication rules with an educational explanation.
